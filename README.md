# 增量区域销售汇总

本地页面：源表（虚构的销售 / 门店）→ 增量批次 → 按区域的订单数、非空金额笔数、金额合计、客单价。

不依赖任何第三方包，只用 Python 3.11 标准库（`http.server` + `sqlite3`）和原生 ES2020 前端。

## 运行

```bash
python3 app.py                 # 默认 http://127.0.0.1:8765/
python3 app.py --port 9000     # 换端口
python3 app.py --db /tmp/x.db  # 换数据库文件
```

首次启动会写入 4 个区域、8 家门店、13 条销售样例，并提交一个初始批次；
之后所有结果都来自 `data/increment.sqlite3`（可用 `APP_DB` 环境变量改路径），
关掉进程再打开仍然存在。页面没有预置报表，所有数字都是已提交批次的累计结果。

页面上的「重置为初始样例」按钮会删掉这个文件并用样例重新播种。

## 聚合规则（`core/aggregation.py`）

| 字段 | 规则 |
| --- | --- |
| 订单数 `order_count` | 所有有效（active）销售记录，含金额为空的和金额为零的 |
| 非空金额笔数 `amount_count` | 金额非空的记录；**0 是存在的金额，计入** |
| 空金额笔数 `null_count` | 金额缺失的记录 |
| 零金额笔数 `zero_count` | 金额恰为 0.00 的记录 |
| 金额合计 `total_cents` | 只累加非空金额（分为单位，整数运算） |
| 客单价 `unit_price_cents` | 合计 ÷ 非空金额笔数，四舍五入到分；没有非空金额时为「未定义」（不是 0.00） |

- 一个分组存在 **当且仅当** 订单数不为 0。区域里最后一条销售被撤回后，该区域
  **不再出现在汇总里**（「无分组」）；只要还有销售（哪怕金额全是空值），区域就仍在，
  此时合计为 0.00（「合计为零」，客单价未定义）。两者在页面、图表和对照表里都分开表示。
- 门店未知或门店未分配区域时，销售进入「未匹配门店 / 未分配区域」桶：会展示，
  但不计入任何区域的合计，也不参与全量对照之外的调整。
- 金额接受字符串或数字，最多两位小数；`null` / `""` / `"null"` / `"none"` / `"~"` 视为空值，
  其他非法金额（如 `"abc"`、`Infinity`、三位小数）整条操作被拒收。

## 批次语义（`core/service.py`）

- **增量台账**：每次变更写 `retract`（撤回旧贡献）与 `add`（加入新贡献）两类有符号条目。
  更新一律先撤回再加入，即使新旧区域相同；门店换区时，该门店下所有销售的旧贡献从旧区域撤回、
  新贡献加入新区域。
- **原子提交**：批次行、逐操作结果、台账、按区域净增量、源表变更、汇总快照、
  同一快照的全量重算结果和逐项对照，全部在同一个 `BEGIN IMMEDIATE` 事务里提交。
- **幂等**：批次身份是规范化载荷的 SHA-256（`format + strict + ops`，`label` 不参与）。
  重复提交同一载荷返回 `replayed`，不会二次累计。
- **拒收**：单条操作可因 `DUPLICATE_KEY` / `INVALID_KEY` / `INVALID_OP` / `NOT_FOUND` /
  `ALREADY_DELETED` / `NO_CHANGE` / `INVALID_AMOUNT` / `UNKNOWN_ZONE` 等被拒，其余操作照常提交（`partial`）；
  插入一个未知门店或未分配区域的门店只记警告并归入「未匹配」桶，不会拒收。
  `strict: true` 时只要有一条被拒，整批不提交；全部被拒时不生成批次、不推进快照版本。
- **故障注入**：载荷带 `fail_after: N` 时，在第 N 条操作的台账写入之后抛出 `SimulatedFailure`，
  事务回滚，批次/明细/汇总/快照都不存在；回滚记录单独写入 `attempts` 审计表，重新提交同一批次即可恢复。

## 页面结构

| 标签页 | 内容 |
| --- | --- |
| 汇总 | 当前区域的指标卡、金额合计条形图（含「无分组」虚线行）、分组明细表、快照版本 |
| 源表 | 可编辑的销售 / 门店行；修改先进入待提交队列，确认后作为一个批次提交 |
| 批次与场景 | 五个可编辑场景（重复键、空金额、区域迁移、删除区域、中途失败恢复）、JSON 批次编辑器、提交结果、批次历史与重放 |
| 变更影响 | 选批次 + 操作序号，看该操作撤回/加入了哪些分组，以及各分组的前值 → 后值 |
| 对照与审计 | 选快照版本，按同一快照的源数据完整重算并逐项对照（6 个度量 × 每个区域）；尝试审计表 |

前端只用类型化的 DOM 构造器拼装节点，不使用 `innerHTML`；所有写操作都经 API 走服务端的
事务与幂等校验，浏览器绕不过去。

## 数据文件

`data/increment.sqlite3`（WAL 模式，`synchronous=FULL`）。主要表：

- `zones` / `stores` / `sales` — 当前源表
- `batches` / `batch_ops` — 批次与逐条操作的接受/拒收结果
- `ledger` — 每个操作的撤回 / 加入明细
- `group_deltas` — 每批次每区域的有符号净增量
- `snapshots` / `summary_groups` / `full_groups` / `reconciliation` — 逐版本汇总、全量重算、逐项对照
- `source_sales_snapshot` / `source_stores_snapshot` — 每个快照所基于的源数据副本
- `attempts` — 提交尝试审计（含被拒、回滚、重放）
